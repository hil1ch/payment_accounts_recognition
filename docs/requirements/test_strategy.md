# Test Strategy — Service for PDF Payment Invoice Recognition

## 1. Цель документа
Определить стратегию тестирования серверной системы и телеграм-бота, реализующих сервис распознавания содержимого платёжных счетов (PDF → JSON).  
Документ описывает подходы, типы тестов, критерии приёмки и аспекты непроизводственных требований.

---

## 2. Область тестирования
Покрываются следующие компоненты:
- FastAPI-сервис `/extract` — загрузка PDF, формирование JSON.
- Telegram-бот — приём файлов, пересылка на API, обработка ответов.
- ML/обработка — пайплайн OCR → извлечение → JSON.
- Контейнеризация (Docker Compose).
- Нагрузочная характеристика (до 100 PDF/мин).

---

## 3. Типы тестов

### 3.1 Unit Tests
**Цель:** Проверить корректность отдельных функций пайплайна:
- Конвертация PDF → изображение.
- OCR-модуль (возврат текста).
- Парсер полей.
- Формирование JSON и обработка спецслов (`__UNKNOWN__`).
- Telegram-бот: корректная обработка сообщений, передача PDF на API.

**Инструменты:** `pytest`.

---

### 3.2 Integration Tests
**Цель:** Проверить взаимодействие модулей OCR → Parser → FastAPI endpoint.

**Проверяем:**
- Корректная передача данных между слоями.
- Валидация формата JSON.
- Обработка ошибок (битый PDF, отсутствующий файл, пустой документ).

**Инструменты:** `pytest` + `httpx` (вызов API).

---

### 3.3 Contract Tests
**Цель:** Гарантировать соответствие API спецификации (вход/выход, коды, структура JSON).

**Проверяем:**
- POST `/extract` возвращает JSON согласно схеме (JSON Schema).
- Неверные запросы → статус 400.
- Ошибки сервера → статус 500 + спецфраза.
- Telegram-бот корректно интерпретирует все коды 2xx/4xx/5xx.

**Инструменты:** `pytest`.

---

### 3.4 E2E Tests (end-to-end)
**Цель:** Проверить полный пользовательский сценарий через Telegram-бот.

**Проверяем:**
1. Отправка PDF в бота → получение JSON в ответ.
2. Отправка не-PDF → корректное сообщение об ошибке.
3. Ответ сервера 5xx → бот отвечает фразой «Сервис временно недоступен».
4. Валидация форматирования JSON в ответном сообщении.

**Инструменты:** `pytest-telegram`.

---

### 3.5 NFR / Load / Performance Tests
**Цель:** Проверить соблюдение нефункциональных требований:

| Требование | Критерий приёмки |
|-------------|------------------|
| **ack ≤ 5 сек** | Сервис подтверждает приём PDF не дольше 5 сек после отправки |
| **avg processing ≤ 1 мин** | Среднее время обработки одного PDF ≤ 60 сек |
| **100 PDF/мин** | Система выдерживает параллельную обработку 100 документов в минуту |

**Инструменты:** `Locust`.

**Метрики:**
- Response time (P95 ≤ 5s).
- Processing duration (P95 ≤ 60s).
- Error rate ≤ 1%.
- CPU/RAM utilization ≤ 80%.

---

### 3.6 Security & Privacy Checks
**Цель:** Проверить соответствие базовым требованиям по защите данных.

**Проверяем:**
- Логи не содержат текстового содержимого документов.
- Временные файлы удаляются после обработки (TTL ≤ 10 мин).
- Нет сохранения истории запросов/результатов.
- API не хранит метаданные пользователей Telegram.
- Защита от повторной отправки (rate limiting опционально).

**Инструменты:** ручная проверка логов, аудит кода, `pytest` с mock-логами.

---

## 4. Privacy Checklist

| № | Проверка | Метод | Ожидаемый результат |
|---|-----------|--------|---------------------|
| 1 | Логи не содержат текст OCR | grep/просмотр логов | Нет фрагментов документа |
| 2 | Временные PDF/PNG удаляются | проверка `/tmp` | Нет файлов после запроса |
| 3 | История запросов не сохраняется | проверка БД / кода | Нет таблиц истории |
| 4 | Нет передачи файлов сторонним сервисам | анализ кода | Используется локальный OCR |
| 5 | TTL промежуточных файлов ≤10 мин | инспекция кода | Временные каталоги очищаются |

---

## 5. Критерии приёмки
- Все API-тесты успешны (2xx/4xx/5xx корректны).
- Среднее время отклика ≤ 5 с.
- Среднее время обработки ≤ 60 с.
- При нагрузке 100 PDF/мин система стабильна ≥10 мин.
- Все privacy-чеклист-пункты пройдены.
