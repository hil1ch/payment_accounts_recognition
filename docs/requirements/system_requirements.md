# Требования к системе

## 1. Функциональные требования (общие)

- **FR-SYS-01:** Приём PDF-скана платёжного счёта через интерфейс Telegram-бота.  
- **FR-SYS-02:** Обработка загруженного PDF и возврат JSON с распознанной структурой документа.  
- **FR-SYS-03:** При невозможности распознать значение поля — в JSON записывается заранее установленное спец-слово (например `"UNKNOWN_VALUE"`).  
- **FR-SYS-04:** Если невозможно распознать наименование поля — в JSON поле не записывается.  
- **FR-SYS-05:** Бот отправляет пользователю текст с отформатированным JSON при ответе сервера `2xx`.  
- **FR-SYS-06:** Бот отправляет спецфразу при ответе сервера `5xx`.  
- **FR-SYS-07:** Бот отправляет заранее подготовленную фразу из набора для `4xx` (в зависимости от кода ошибки/типа ошибки).  
- **FR-SYS-08:** Отсутствие персистентного хранения истории запросов.  

---

## 2. Нефункциональные требования (общие)

- **NFR-PERF-01:** Среднее время обработки одного документа на сервере ≤ 1 мин.  
- **NFR-THR-01:** Система должна выдерживать одновременную загрузку до 100 PDF/мин.  
- **NFR-SEC-01:** Передача файлов по HTTPS.  
- **NFR-SEC-02:** При использовании очередей сообщений данные должны быть защищены:
  1. Передача только по зашифрованному каналу (TLS 1.2+).  
  2. Сообщения на диске брокера должны храниться в зашифрованном виде.  
- **NFR-AUTH-01:** Бот-серверный канал аутентифицирован.  
- **NFR-LOG-01:** Логирование ошибок (без хранения содержимого документов).  
- **NFR-CONTAINER-01:** Приложение контейнеризовано; запуск одной командой `docker compose up --build`.  
- **NFR-REPRO-01:** Jupyter-notebook должен быть воспроизводим. Фиксировать гиперпараметры и случайные значения.  

---

## 3. Telegram-бот — функциональные требования

- **BOT-FR-01:** Принимает PDF файлы и подтверждает приём.  
- **BOT-FR-02:** Пересылает файл на HTTP endpoint (`multipart/form-data`).  
- **BOT-FR-03:** Обрабатывает коды ответа сервера:  
  - `2xx`: отправляет пользователю отформатированный JSON.  
  - `4xx`: отправляет заранее подготовленную фразу из набора (например `INVALID_FORMAT`, `FILE_TOO_LARGE`, `UNAUTHORIZED`).  
  - `5xx`: отправляет спецфразу (например `SERVICE_TEMPORARILY_UNAVAILABLE`).  
- **BOT-FR-04:** Поддерживает команды `/start`, `/help`.  

---

## 4. Telegram-бот — нефункциональные требования

- **BOT-NFR-01:** Время реакции бота ≤ 5 сек на подтверждение приёма файла (загрузка файла и асинхронная отправка его в обработку).  
- **BOT-NFR-02:** Поддержка до 100 одновременных активных чатов.  

---

## 5. HTTP API — функциональные требования

- **API-FR-01:** Endpoint `POST /api/v1/parse` — принимает PDF и возвращает JSON.  
- **API-FR-02:** В теле ответа указывать метаданные: `processing_time_ms`, `model_version`, `status` (удалось ли распознать ключевые поля).  
- **API-FR-03:** Код ответа и поведение как в ТЗ (`2xx` успешные, `4xx` клиентские, `5xx` серверные).  

---

## 6. HTTP API — нефункциональные требования

- **API-NFR-01:** Документация в Swagger/OpenAPI.  
- **API-NFR-02:** Валидация входных данных (макс. размер файла, MIME-type).  
- **API-NFR-03:** Таймауты на обработку и корректные ответы при превышении.  

---

## 7. ML-модель / пайплайн — функциональные требования

- **ML-FR-01:** Распознавать ключевые поля: поставщик, покупатель, общая сумма, НДС.  
- **ML-FR-02:** При неопределённости значения записывать спецслово (`UNKNOWN_VALUE`).  
- **ML-FR-03:** Модель должна уметь обрабатывать таблицы.  
- **ML-FR-04:** Модель должна корректно распознавать ключевые поля (поставщик, покупатель, общая сумма, НДС) в платёжных документах с различной структурой и расположением данных (например: разные форматы таблиц, различное расположение реквизитов, разные шрифты).  
- **ML-FR-05:** Модель должна выделять нужные поля из текста (например, НДС).  

---

## 8. ML-модель / пайплайн — нефункциональные требования

- **ML-NFR-01:** Модель версионируется (`model_version` в ответе).  
- **ML-NFR-02:** Модель должна иметь метрики оценки точности.  
- **ML-NFR-03:** Весь пайплайн создания модели должен быть воспроизводим.
